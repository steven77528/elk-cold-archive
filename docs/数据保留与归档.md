## 1. 范围与存储分层

本文覆盖下列业务数据流的在线保留和 OSS 离线归档：

- `logs-gateway-*`
- `logs-nginx-*`
- `logs-hdg-hdg`
- `logs-standalone-*`

系统索引、Kibana 索引、`logs-hdg-cabinet` 和未列出的数据流不属于自动归档范围。新增范围前，必须完成
数据分类、保留期审批和恢复演练。

| 数据层 | 实际位置 | 查询方式 | 用途 |
| --- | --- | --- | --- |
| 热数据 | Elasticsearch `data_hot` | Kibana / Elasticsearch API | 最新且持续写入的数据 |
| 温数据 | Elasticsearch `data_warm` | Kibana / Elasticsearch API | 已 rollover 的在线数据 |
| 离线归档 | 阿里云 OSS Snapshot | 恢复后查询 | 长期、低成本保留 |

当前架构不使用 Elasticsearch `data_cold` 节点。ILM 只保留 hot 和 warm phase；OSS Snapshot 是离线归档，
不能直接在 Kibana 中查询。恢复操作见[OSS 快照数据恢复操作手册](OSS快照数据恢复操作手册.md)。

## 2. 保留规则

| 类别 | 数据流 | ILM | 热/温在线时间 | 归档候选窗口 | OSS 固定保留期 |
| --- | --- | --- | --- | --- | ---: |
| Gateway | `logs-gateway-*` | `gateway` | hot 0-5 天；warm 5-10 天 | 10-20 天 | 10 天 |
| Nginx | `logs-nginx-*` | `nginx` | hot 0-7 天；warm 7-15 天 | 15-30 天 | 15 天 |
| HDG | `logs-hdg-hdg` | `default` | hot 0-15 天；warm 15-45 天 | 45-225 天 | 180 天 |
| Standalone | `logs-standalone-*` | `default` | hot 0-15 天；warm 15-45 天 | 45-225 天 | 180 天 |

Rollover 条件为最长 1 天或单个主分片 20 GB，任一条件先满足即 rollover。表中的年龄是 backing index 的
rollover 年龄，不是日志的 `@timestamp`，也不使用索引名或 `creation_date` 推算。

候选窗口上限是安全上限，不是强制删除日。超过上限只会产生 overdue 告警，不会自动快照或删除。归档任务
延迟会延长实际总保留期；OSS 保留期从 Snapshot 成功完成时开始计算。

## 3. 归档流程与安全边界

```text
写入当前 write index
  -> ILM rollover
  -> hot / warm 在线保留
  -> 到达归档窗口
  -> 对候选所属完整数据流创建 Snapshot
  -> 验证 Snapshot SUCCESS
  -> 删除本次审核通过的精确 backing index
  -> 按固定保留期清理 Snapshot
```

程序会对候选所属的完整数据流创建 Snapshot，但只删除本次通过检查的精确 backing index。Snapshot 中包含
未到龄 backing index 是正常现象，不能据此删除它们。

生产删除前必须同时满足：集群 UUID 正确、集群不是 red、目标不是当前 write index、Snapshot 为完整
`SUCCESS`、failed shard 为 0、Snapshot 包含全部候选，并且每个删除前都重新核对数据流归属和 index UUID。

OSS 仓库为 `oss_s3_backup`，UUID 为 `V_kt03p6SkWfmq6l_R8P6g`，bucket 为 `hycen-elk-cold-data`，
base path 为 `elasticsearch/snapshots`。访问密钥仅能保存在 Elasticsearch keystore。

不得直接删除或修改 OSS `elasticsearch/snapshots` 下的对象，也不得用 OSS 生命周期规则清理它。Snapshot
会跨快照共享 segment，所有清理都必须走 Elasticsearch Delete Snapshot API。

## 4. 日常操作

### 查看状态

在归档服务器执行：

```bash
cd /data/monitor/elk-cold-archive

docker compose ps
docker compose logs --tail=200 cold-archive
tail -n 100 data/audit.jsonl
```

调度器每天 `02:00 Asia/Shanghai` 运行。失败退出码 `1` 时每 30 分钟重试，最多重试两次；退出码 `0`、`2`、`3`
不自动重试。

### Dry-run(一般不用)

先执行 dry-run。它不会创建 Snapshot、删除索引或删除 Snapshot：

```bash
cd /data/monitor/elk-cold-archive

docker compose run --rm \
  -e ARCHIVE_EXECUTE=false \
  cold-archive --once --dry-run
```

放行 live 前必须确认：候选仅属于预期数据流和年龄窗口，`Overdue=0`，没有 repository、UUID、
rollover metadata、override 或邮件错误，且 `Snapshots=0`、`Deleted=0`、`Deleted snapshots=0`。

### 手工正式执行(一般不用)

只有 dry-run 已审批、没有未完成事务、仓库没有运行中的 Snapshot，且恢复演练已通过时才允许执行：

```bash
cd /data/monitor/elk-cold-archive

docker compose run --rm cold-archive --once --execute
```

执行后确认每批均有 `snapshot_verified`、`index_deleted` 和 `transaction_complete` 审计记录；Snapshot 为
完整 `SUCCESS`；`Deleted` 与审核清单一致；`data/transaction.json` 已消失。

归档周期启用前，服务器 `.env` 应设置 `ARCHIVE_EXECUTE=true`，然后重建调度容器：

```bash
cd /data/monitor/elk-cold-archive

docker compose up -d --force-recreate cold-archive
docker compose ps
```

## 5. 监控与 Snapshot 清理

外部监控至少覆盖以下项目：

- `cold-archive` 容器状态和 health。
- `/state/heartbeat` 是否超过 180 秒未更新。
- `/state/scheduler.json` 的最后完成时间、模式和退出码。
- `/state/transaction.json` 是否持续存在。
- `GET /_snapshot/oss_s3_backup/_status` 是否存在长时间运行的 Snapshot。
- 每日摘要中的 Candidates、Overdue、Expired snapshots、warnings 和 errors。
- 在线 Elasticsearch 磁盘水位及 unassigned primary shard 数量。

迁移或恢复演练期间，保持 Snapshot 自动清理关闭：

```json
{
  "snapshot_cleanup": {
    "enabled": false,
    "max_deletions_per_run": 30
  }
}
```

恢复演练通过后才启用清理。每个 Snapshot 创建时会固定记录 10、15 或 180 天的 `retention_days`；后续改
规则不会修改已有 Snapshot 的保留期。每次最多删除 30 个到期 Snapshot。

仓库中仍存在某数据流的受管 Snapshot 时，不要删除或重命名该数据流对应的归档规则 pattern。否则自动
清理会跳过这些 Snapshot 并告警。

## 6. 异常与变更

### 未完成事务

发现 `data/transaction.json` 时，禁止手工删除文件、删除或重用事务中的 Snapshot 名称。检查 Snapshot
状态和审计日志，修复故障后以相同生产集群和相同配置重新执行一次 live，让程序验证原 Snapshot 并续作。

事务完成后才会写入 `transaction_complete` 并清理事务文件。事务绑定生产 cluster UUID，不能在其他
集群继续执行。

### 常见异常

| 场景 | 运维动作 |
| --- | --- |
| overdue | 查明调度中断或容量问题；不得跳过 Snapshot 验证直接删索引。 |
| Snapshot 超时、FAILED 或 PARTIAL | 保留事务，修复分片或仓库后让 live 续作。 |
| 邮件失败，退出码 3 | 先查审计、Snapshot 和 Deleted；归档可能已经成功。 |
| `rollover_info` 缺失 | 停止 live；仅可对人工审核的精确索引和 UUID 使用一次性覆盖。 |
| 仓库身份不匹配 | 核对 repository UUID、类型和 settings，禁止绕过校验。 |

一次性 rollover 时间覆盖只用于恢复后且确实没有 `rollover_info` 的历史索引。必须精确核对索引名、UUID、
数据流归属、非 write index 身份和人工时间依据；完成一次 live 后立即删除覆盖并执行 clean dry-run。

调整 ILM、模板、归档规则或保留期前后，至少完成：记录审批与回滚方式、确认模板/ILM/规则匹配、确认已有
受管 Snapshot 仍能匹配规则、执行 clean dry-run、完成代表性恢复查询，并观察一个完整 rollover 和归档周期。
